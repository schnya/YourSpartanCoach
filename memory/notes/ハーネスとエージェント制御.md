# ハーネスとエージェント制御

**要約**: どんなAIエージェントでも、実装は「ループ制御・コンテキスト管理・ツール実行・状態・エラー・権限」の6レイヤーでできている。フレームワークを使う前に生APIで最小ループを書くのが、設計を体感で理解する近道。

どんなエージェントでも、ハーネスは大体この6つのレイヤーでできています。

**1. ループ制御（Agent Loop）** モデルを1回呼んで終わりではなく、「モデルの出力を見る→ツールを実行する→結果をモデルに返す→また呼ぶ」を繰り返す仕組み。終了条件（タスク完了、最大ステップ数、エラー多発）をどう決めるかが設計の肝です。

**2. コンテキスト管理** 何をモデルに見せるか。会話履歴を全部積むとすぐトークン上限に達するので、「古い履歴を要約する」「関連ファイルだけ取得する」「必要な時だけツールで情報を取りに行かせる」といった取捨選択が必要です。ここの設計がコストと精度を一番左右します。

**3. ツール実行層** モデルが「このツールをこの引数で呼びたい」と言った時、実際にコードを実行して結果を返す部分。ここで重要なのは:

- 入力のバリデーション（モデルが変な引数を渡してきても壊れないように）
- タイムアウトとリトライ戦略
- 副作用のあるツール（メール送信、DB書き込みなど）は確認ステップを挟むか

**4. 状態・メモリ管理** 1回のタスク内の状態（今どのファイルを編集中か等）と、セッションをまたぐ記憶（過去のやり取り）は別物として設計するのが普通です。

**5. エラーハンドリング** ツール呼び出し失敗、モデルの出力がパースできない、無限ループに陥る——これらにどう対処するか。「n回失敗したら人間にエスカレーション」のような安全弁が必要です。

**6. 権限・ガードレール** エージェントがどのツールを使えるか、どのデータにアクセスできるか。特に自動実行系（ファイル削除、送金、外部送信など）は「実行前に確認」を挟むかどうかの設計判断が要ります。

## 実装土台の比較

|選択肢|向いてるケース|トレードオフ|
|---|---|---|
|**生API + 自作**|学習目的、細かい制御が必要、既存フレームワークの抽象化が邪魔になる場合|全部自分で書く。ループ、リトライ、状態管理、全部手動|
|**LangChain/LlamaIndex等**|素早くプロトタイピング、RAGなど定型パターンが多い|抽象化が重く、デバッグしづらいことがある。バージョン変化が激しい|
|**Claude Agent SDK / Copilot SDK等の公式SDK**|プロバイダのベストプラクティスに乗りたい、本番運用実績のあるハーネスが欲しい|特定プロバイダに縛られやすい|

**個人的におすすめする進め方**は、まず生APIで最小限のループ（モデル呼び出し→ツール実行→結果を返す、を3〜4回転させるだけ）を自分で書いてみることです。ここを一度手で書くと、フレームワークが何を肩代わりしてくれているのかが体感でわかります。その後、必要に応じてSDKやフレームワークに乗り換えると、「なぜそのフレームワークがそう設計されているか」が理解しやすくなります。
