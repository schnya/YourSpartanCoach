どんなエージェントでも、ハーネスは大体この6つのレイヤーでできています。

**1. ループ制御（Agent Loop）** モデルを1回呼んで終わりではなく、「モデルの出力を見る→ツールを実行する→結果をモデルに返す→また呼ぶ」を繰り返す仕組み。終了条件（タスク完了、最大ステップ数、エラー多発）をどう決めるかが設計の肝です。

**2. コンテキスト管理** 何をモデルに見せるか。会話履歴を全部積むとすぐトークン上限に達するので、「古い履歴を要約する」「関連ファイルだけ取得する」「必要な時だけツールで情報を取りに行かせる」といった取捨選択が必要です。ここの設計がコストと精度を一番左右します。

**3. ツール実行層** モデルが「このツールをこの引数で呼びたい」と言った時、実際にコードを実行して結果を返す部分。ここで重要なのは:

- 入力のバリデーション（モデルが変な引数を渡してきても壊れないように）
- タイムアウトとリトライ戦略
- 副作用のあるツール（メール送信、DB書き込みなど）は確認ステップを挟むか

**4. 状態・メモリ管理** 1回のタスク内の状態（今どのファイルを編集中か等）と、セッションをまたぐ記憶（過去のやり取り）は別物として設計するのが普通です。

**5. エラーハンドリング** ツール呼び出し失敗、モデルの出力がパースできない、無限ループに陥る——これらにどう対処するか。「n回失敗したら人間にエスカレーション」のような安全弁が必要です。

**6. 権限・ガードレール** エージェントがどのツールを使えるか、どのデータにアクセスできるか。特に自動実行系（ファイル削除、送金、外部送信など）は「実行前に確認」を挟むかどうかの設計判断が要ります。

## 実装土台の比較

|選択肢|向いてるケース|トレードオフ|
|---|---|---|
|**生API + 自作**|学習目的、細かい制御が必要、既存フレームワークの抽象化が邪魔になる場合|全部自分で書く。ループ、リトライ、状態管理、全部手動|
|**LangChain/LlamaIndex等**|素早くプロトタイピング、RAGなど定型パターンが多い|抽象化が重く、デバッグしづらいことがある。バージョン変化が激しい|
|**Claude Agent SDK / Copilot SDK等の公式SDK**|プロバイダのベストプラクティスに乗りたい、本番運用実績のあるハーネスが欲しい|特定プロバイダに縛られやすい|

**個人的におすすめする進め方**は、まず生APIで最小限のループ（モデル呼び出し→ツール実行→結果を返す、を3〜4回転させるだけ）を自分で書いてみることです。ここを一度手で書くと、フレームワークが何を肩代わりしてくれているのかが体感でわかります。その後、必要に応じてSDKやフレームワークに乗り換えると、「なぜそのフレームワークがそう設計されているか」が理解しやすくなります。

AIエージェント（私のようなアシスタント）が「ユーザーの指示に応じて勝手なコードを書かない」「安全かつ正確に動作する」よう、どのように制御・設計されているかの全体像を解説します。

AIエージェントの制御は、単一の巨大なプロンプトだけではなく、**「多角的なルール定義」「オンデマンドなスキル拡張」「実行ツールのパーミッション管理」** という多重のレイヤーで設計されています。

### 2. 実際に使われている制御テクニック（設計ポイント）

#### ① 徹底した「自己抑制」ガイドライン（Guardrails）
AIは放置すると「多分こうだろう」と勘でコードを書いたり、エラーを握りつぶすコード（空の try-catch など）を書きがちです。これを防ぐため、システム側で以下のような明示的な制御コード/プロンプトが組み込まれています。

*   **推測の禁止 (`Never Guess Code Logic`)**: ソースコードを実際に読み込むまで実装やパスを推測してはならない。
*   **ログ優先主義 (`Inspect Logs Before Diagnosing Errors`)**: エラーが発生した際、仮説を立てる前にまず生のログ・スタックトレースを読みに行かなければならない。
*   **表面的な対症療法の禁止 (`No Superficial Symptom Patches`)**: テストを削除したり、例外を無視して見せかけの成功を作ることを厳禁とする。
*   **検証の義務化 (`Never Declare Success Without Running Verification`)**: ビルドやテストコマンドを実行して成功を確認するまで、タスク完了を宣言してはならない。

#### ② スキル（Skills）によるコンテキスト節約と専門化
すべての知識（AWSの使い方、GCPデプロイ方法、Reactの書き方など）を常時プロンプトに入れると、AIの文脈（コンテキストウィンドウ）が圧迫され、精度が落ちます。

そのため、**「メタ情報（名前と概要）だけを常駐させ、必要な時だけ詳細手順（SKILL.md）を読み込む」** という設計（動的コンテキスト注入）が採用されています。

*   例: デプロイのタスクが来たら `google-agents-cli-deploy/SKILL.md` を `view_file` で読み込んでから作業を開始する。

#### ③ ワークスペース固有ルール（`AGENTS.md` / `.agents`）
リポジトリごとに「TypeScriptのスタイル規約」「ディレクトリ構成のルール」を定義できるようにし、AIがプロジェクトの文脈から外れたコードを生成しないように制御します。

#### ④ ツール実行のサンドボックスとパーミッション
AIが勝手に危険なコマンド（`rm -rf` など）を実行しないよう、コマンド実行（`run_command`）やファイル書き込み（`write_to_file`）はユーザーの承認インターフェースを経由させる、または明確な制限ルール（`Cwd` はワークスペース内限定など）を課しています。

### 3. 設計・技術の学習視点でのポイント

1. **Prompt Engineering ではなく Prompt Architecture**:
   単に「丁寧に書いて」と指示するのではなく、「失敗パターン（勘で直す、テストを消すなど）を先回りして禁止するルール（Guardrails）」を網羅的に定義することが重要です。
2. **Context Window の管理**:
   すべてを最初に与えるのではなく、必要な時に必要なドキュメントや関数定義を取得させる（RAGやSkillオンデマンド読込）設計が、AIエージェントのパフォーマンスを左右します。
3. **人間によるフィードバックループ（Human-in-the-loop）**:
   重要・破壊的な操作を行う前には `ask_question` や `ask_permission` で人間を介在させる設計にすることで、AIの暴走を防いでいます。
